Changelog OpenD578 V11.7

Date de publication : 5 novembre 2026 Version précédente : V11.6 Commit de la release : 9124d7e Cible étudiée : AnyTone AT-D578UV PRO, GD32, application constructeur V1.21.

Cette release ajoute le décodage du voyant de statut, un inventaire des fonctions à qualifier et des rapports d’auto-test ouverts. Le voyant suit les commandes GPIO réellement émises par le firmware. L’inventaire et les rapports distinguent les fonctions documentées, les modèles partiels et les essais exécutés.

Il s’agit d’une release du banc de simulation et de ses outils. Elle ne fournit pas encore un firmware OpenD578 installable sur le poste.

Ajouté

Décodage du voyant rouge/vert du poste

  • Nouveau modèle bench/status_led.py.
  • Lecture du bus série : PE3 = données, PE4 = horloge.
  • Échantillonnage des données sur les fronts montants de l’horloge.
  • Assemblage de mots de 8 bits, bit de poids faible en premier.
  • Décodage du vert depuis le masque 0x08, et du rouge depuis 0x10.
  • Affichage du voyant dans le banc à partir de la commande décodée.
  • Exposition de l’octet brut, des bits encore incomplets et d’un historique borné.
  • Réutilisation du décodeur dans le mode matériel, sans dépendance à une adresse de routine ou à une variable RAM de l’OEM.

Avant la réception d’un mot complet, le voyant reste inconnu. La reprise rapide depuis l’ancienne capture RAM ne fabrique pas une commande qui n’a pas été enregistrée. Les autres bits du mot de commande restent sans fonction lumineuse attribuée.

Ces entrées ne correspondent pas à 117 fonctions OEM confirmées sur cette variante. Elles comprennent des fonctions documentées pour la famille D578, des fonctions conditionnelles, des exigences de test et les extensions du projet. Le satellite est identifié comme une extension OpenD578. La réception APRS reste une étape ultérieure.

Chaque entrée possède un identifiant, des sources et leur niveau de preuve, un état du modèle, un critère d’acceptation et les blocages connus. Le catalogue livré classe 17 modèles comme partiels et 100 comme non implémentés ; ces états ne sont pas des verdicts de conformité du firmware.

Formats fournis :

  • bench/qualification_data/catalog.json : catalogue de référence.
  • bench/qualification_data/catalog.schema.json : schéma JSON Schema 2020-12.
  • docs/FUNCTION_MATRIX.csv : vue tabulaire du catalogue.

Les fonctions OEM précédemment jugées supprimables restent recensées, afin de conserver la connaissance de leur existence. Leur présence dans l’inventaire ne les rend pas obligatoires pour la première version du firmware ouvert.

Exploration reproductible du firmware

Le nouvel outil bench/oem_discovery.py relève :

  • l’empreinte et l’adresse de chargement de l’image ;
  • des candidats d’entrées de code ;
  • des constantes candidates de périphériques ;
  • des textes candidats associés aux mots-clés du catalogue ;
  • des pointeurs alignés possibles vers ces textes ;
  • les limites de l’analyse et les catégories encore non résolues.

Sur l’application PRO GD32 V1.21 étudiée, l’analyse relève 3 042 candidats d’entrées et des textes candidats associés à 110 entrées du catalogue. Ces nombres ne constituent ni un décompte fiable des fonctions, ni un taux de couverture fonctionnelle. Les motifs peuvent aussi rencontrer des données, des ressources partagées et des références sans lien avec la fonction cherchée.

Le rapport public docs/firmware_discovery_v121.json conserve les adresses et remplace les textes candidats par leurs empreintes et leurs longueurs. L’image constructeur n’est pas incluse dans les sources publiables.

Auto-test et rapports JSON/JUnit

  • Nouveaux lanceurs TESTER_BASES.cmd et TESTER_BASES.sh.
  • Nouveau gestionnaire bench/run_base_tests.py.
  • Nouveau générateur de couverture bench/selftest_report.py.
  • Ajout de --case à bench/run_bench.py pour choisir un scénario.
  • Nouveau scénario bench/scenarios/LED_RX_TX.json.
  • Nouveau critère de verdict bench/indicator_qualification.py pour les voyants.
  • Rapports qualification.json, selftest.json et junit.xml.
  • Sous-dossier distinct pour chaque campagne lancée par TESTER_BASES.

Les exigences non qualifiées restent incomplete dans le JSON et skipped dans le JUnit. Un essai absent ou un périphérique non modélisé ne devient pas un succès. Un échec constaté reste un échec dans les rapports.

Le critère LED_bus compare les stimuli externes et les réponses du bus GPIO. Il n’utilise aucune variable OEM de réception ou d’émission. Il peut aussi examiner une trace compatible produite par le mode matériel. Les trois critères historiques FM/GPS/PTT utilisent encore des observations spécifiques à V1.21.

Observations matérielles explicites

Le nouveau module bench/board_observations.py expose les sorties observées :

  • registres bruts GPIO et éclairage ;
  • commande du voyant de statut ;
  • trames radio vers microphone ;
  • état connu ou inconnu des indicateurs du microphone ;
  • état non qualifié des routes audio ;
  • périmètre réel du modèle Bluetooth.

Les sorties audio non qualifiées restent à selected: null. L’état logiciel TX de l’OEM ne suffit pas à déclarer une LED allumée ou un haut-parleur actif.

Modifié et corrigé

  • Le voyant de statut, auparavant neutre faute de décodeur, suit maintenant la liaison PE3/PE4.
  • La restauration d’une session conserve la séparation des composants du simulateur ; le nouveau décodeur n’invente pas son historique absent d’une ancienne capture.
  • La page présente les trames sortantes du microphone sans attribuer de sens non vérifié à leurs champs.
  • La ligne USB du tableau matériel indique la présence de l’hôte simulé et l’état CDC observé, au lieu d’afficher systématiquement un hôte absent.
  • Le message de fermeture renvoie au lanceur V11.7.
  • Les empreintes de version prennent en compte les nouveaux composants et ressources concernés, pour éviter la réutilisation d’un serveur périmé.
  • Les README décrivent la qualification V11.7 et séparent les essais bornés de la validation matérielle complète.

Nouvelles informations apprises

Commandes du voyant et recoupement bootloader/application

Le bootloader du dump complet contient une routine à 0x080042BA qui transmet huit bits sur PE3/PE4. La boucle de mise à jour l’appelle alternativement avec 0x00 et 0x10. Ce comportement est cohérent avec le clignotement rouge observé sur le poste en mode de mise à jour.

Dans l’application V1.21, le chemin correspondant se trouve autour de 0x0808A400. Les retours d’appels GPIO relevés comprennent 0x0808A416, 0x0808A424, 0x0808A42E, 0x0808A43C et 0x0808A454. Ces adresses servent à documenter l’analyse ; le nouveau décodeur n’en dépend pas.

L’exécution du scénario donne :

Situation du scénario Commande Bit vert 0x08 Bit rouge 0x10
Réception avec squelch ouvert 0x4E 1 0
Repos après retrait de la porteuse 0x46 0 0
Émission après PTT 0x56 0 1
Repos après relâchement 0x46 0 0

Niveau de preuve : les commandes et les fronts GPIO ont été observés dans le firmware exécuté. La correspondance des couleurs est déduite de ces traces, du bootloader et des observations utilisateur. La continuité électrique et la référence du circuit pilote n’ont pas été mesurées.

Le scénario ne détermine pas le comportement du voyant avec un CTCSS incorrect, pendant tous les modes de balayage ou pour les autres couleurs éventuelles. Le squelch porteuse et la porte audio n’évoluent pas exactement au même instant.

Dialogue radio vers microphone

Des trames sortantes de 16 octets, commençant par 0x53 et se terminant par 0x06, ont été enregistrées sur USART0. Leur structure est désormais exposée dans le banc. La signification des champs concernant les LED et le routage audio reste à déterminer.

Le modèle OEM emploie aussi une activité microphone synthétique, avec un 0x06 périodique. Cela ne démontre pas que le microcontrôleur du microphone est émulé ou qu’il a exécuté les commandes reçues.

Haut-parleur du microphone et routes audio

Le haut-parleur sélectionnable du microphone est ajouté au périmètre. Il faut qualifier séparément :

  • le haut-parleur interne du poste ;
  • celui du microphone, avec sélection de la voie A ou B ;
  • les sorties externes A et B ;
  • les chemins audio Bluetooth.

Les choix microphone/poste/les deux et les effets des contacts des prises externes doivent être vérifiés. La boucle audio du navigateur ne suffit pas à prouver le routage du matériel simulé.

Texte présent dans le firmware et capacité réelle

L’image PRO V1.21 contient le texte APRS Receive. Cette présence ne prouve pas que le poste capturé sait recevoir l’APRS. Une ressource peut être partagée entre variantes ou appartenir à une branche désactivée. Le nouvel outil maintient ces occurrences au niveau de pistes, sans en déduire une fonction opérationnelle.

Bluetooth

L’option Bluetooth fait partie du catalogue. Une référence ET12/B707 est connue dans les travaux du projet et le modèle existant couvre quelques commandes AT de version et d’AGHF.

La disponibilité d’un firmware ne suffit pas à permettre son exécution : processeur, jeu d’instructions, mémoire et interfaces doivent être établis. Le module n’exécute pas encore son firmware dans le simulateur. L’appairage, la reconnexion, le PTT et les échantillons audio Bluetooth restent à modéliser.

Anciennes informations de brochage et photographies

La table des 100 broches a été relue. Certaines mentions anciennes NON CONNECTE étaient des emplacements non renseignés ; elles ne démontrent pas une absence de connexion. Les hypothèses issues d’autres cartes restent à distinguer des connexions mesurées sur le D578 étudié.

Les liens FCC ont été conservés, mais les photographies n’ont pas été réinspectées dans cette release après l’échec de leur récupération. Les entrées FCC de schémas visibles uniquement comme métadonnées ne sont pas considérées comme des schémas effectivement obtenus.

Utilisation et compatibilité

Extraire la V11.7 dans un nouveau dossier puis lancer OUVRIR_BANC_WEB_V11_7.cmd sous Windows, ou le lanceur correspondant au système.

Le voyant peut rester inconnu après une reprise rapide jusqu’à l’émission de sa première commande complète. Les autres nouvelles observations apparaissent dans l’IHM et dans les données du moteur.

Pour les essais de base, arrêter le moteur web puis lancer :

TESTER_BASES.cmd --source-dir "C:\D578\captures"

Dans les sources du dépôt :

python bench/run_bench.py --source-dir /chemin/captures --engine native
python bench/run_bench.py --source-dir /chemin/captures --engine native --case LED_bus
python bench/selftest_report.py --regressions bench/results/bench/qualification.json

run_bench.py conserve son code de sortie pour les scénarios sélectionnés. selftest_report.py renvoie 2 pour une qualification incomplète et 1 en cas d’échec. Un code 2 ne signifie donc pas que le poste est en panne. Le lanceur TESTER_BASES place chaque campagne dans un sous-dossier de results/bench et termine sur le verdict de couverture.

Pour un firmware entièrement différent, utiliser le mode matériel run_hardware.py. Le décodeur du voyant y est réutilisable ; les autres critères spécifiques aux adresses et structures V1.21 doivent être remplacés par des observations matérielles indépendantes. Aucun verdict global automatique pour un firmware arbitraire n’est annoncé dans cette release.
